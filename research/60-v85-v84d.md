## 2. v85：`81db71cfba0` 落地复核

### 2.1 与上游逐字对照

**两处 hunk 的"改动行"完全相同**（注释 + `cs_load32_to` + `cs_store32`），只有 hunk 头行号不同（本树在函数上方有本地新增 ⇒ 偏移；`cmd_dispatch` 上游 `@@ -391` vs 本树 `@@ -429`）。

```diff
  /* src/panfrost/vulkan/csf/panvk_vX_cmd_dispatch.c :429 起（本树） */
-   /* Copy the global TLS pointer to the per-job TSD. */
+   /* Copy the global TLS pointer and size to the per-job TSD. */
    if (cs->info.tls_size) {
       cs_move64_to(b, cs_scratch_reg64(b, 0), cmdbuf->state.tls.desc.gpu);
+      cs_load32_to(b, cs_scratch_reg32(b, 4), cs_scratch_reg64(b, 0), 0);
       cs_load64_to(b, cs_scratch_reg64(b, 2), cs_scratch_reg64(b, 0), 8);
       cs_move64_to(b, cs_scratch_reg64(b, 0), tsd);
+      cs_store32(b, cs_scratch_reg32(b, 4), cs_scratch_reg64(b, 0), 0);
       cs_store64(b, cs_scratch_reg64(b, 2), cs_scratch_reg64(b, 0), 8);
       cs_flush_stores(b);
    }
```
`csf/panvk_vX_cmd_precomp.c` 同型（`@@ -64` 起）。

- 备份：`csf/panvk_vX_cmd_dispatch.c.bak-v85-1791221540`（18991 B）· `csf/panvk_vX_cmd_precomp.c.bak-v85-1791221540`（7368 B）
- **语义**：旧代码只把 **TLS 指针**（8 B @ tsd+8）复制到 per-job TSD；新代码把 **TLS 尺寸**（u32 @ tsd+0，从 `cmdbuf->state.tls.desc.gpu` 的第 0 个字读）也复制过去。仅当 `tls_size != 0` 时执行。
- 为何与我们的症状相关（59 号 §4.1 已论证）：TSD 里的 TLS 尺寸陈旧/为零 ⇒ 计算作业的 TLS 分配被低估 ⇒ 共享/TLS 越界写 ⇒ 可能污染顶点/索引/描述符缓冲 ⇒ 几何偏移/巨型三角。**收益上限取决于"我们是否真走带 TLS 的 compute"——本报告未验证**（见 §5）。

**"纯诊断版"的证据链**：
1. 驱动 `.so` 与 v84 **逐字节相同** ⇒ 只有 env（与 versionCode）在变 ⇒ **严格单变量**。
2. manifest 长度 3588 B，而 v84-nodiag 是 3568 B（**+20 B**）；其中 `PANVK_DEBUG=1,kbase_diag` 比 `PANVK_DEBUG=0` **多 12 个字符**，余下 8 B 与 versionCode/versionName 的改动相符 ⇒ **间接一致**。
3. 限制：我**未能**从 binary XML 里直接解出 `PANVK_DEBUG=…` 字符串（`strings` 未命中；AAPT 反编译未做）⇒ 第 2 条是**长度算术推断**，不是直接读出。若需硬证据，用 `aapt2 dump xmltree` 或让 Lead 确认打包命令（一行）。

**用途**：它是 `/root/research/60b-hang-playbook.md` 的取证工具——**只有 `PANVK_DEBUG=kbase_diag` 下**，`marks`/`stream progress`/`CKPT` 字/`ENTRY` 解码才被写入与打印；nodiag 版跑出来的这些字段**恒为 0**，不能用于定位。
