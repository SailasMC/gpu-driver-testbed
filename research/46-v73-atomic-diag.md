## 1. SYNC_ADD64 emission point

**`src/panfrost/vulkan/csf/panvk_vX_gpu_queue.c:1357`** (v73 tree; same statement is **:1291** in the
v72 tree — the +66 shift is +1 for the `dev` local at :835 and +65 for the ATOMIC block at :906-970):

```c
1356:   cs_move64_to(&b, val64, 1);
1357:   cs_sync64_add(&b, true, MALI_CS_SYNC_SCOPE_SYSTEM, val64, addr64,
1358:                 cs_defer(0, SB_ID(DEFERRED_SYNC)));
1359:
1360:   /* Fault-recovery boundary, matching the panthor kernel sequence. */
1361:   cs_error_barrier(&b);
1362:   cs_end(&b);
```

This is the **only** instruction that advances the subqueue seqno cell; nothing is emitted after it
except a register-less `ERROR_BARRIER`. It is emitted on **every** ring job, so it is the last thing
the wrapper does before the hang — which is exactly why v72 stopped at ID 42.

Builder side:
- `cs_sync64_add` is generated by `CS_SYNC_OPS(64)` — **`src/panfrost/genxml/cs_builder.h:2318`**,
  expanding the macro `cs_sync##__cnt_width##_add` at **`cs_builder.h:2289`**.
- That macro sets `I.data = cs_src##__cnt_width(b, val)` and `I.address = cs_src64(b, addr)`
  (**`cs_builder.h:2299-2300`**). `cs_src64()` (**`cs_builder.h:383`**) is a plain 2-register
  tuple — **it carries no offset**. So the atomic writes to `addr64 + 0`.

Contrast that with the wrapper's diagnostic STOREs, which *do* take an explicit offset
(`cs_store32(b, val32, addr64, KBASE_SEQNO_CHECKPOINT_OFFSET)`, offset 56 = `:92`). The SYNC_ADD64
has no such offset ⇒ **it targets the seqno word at cell + 0**.

### Where `backend_mem_flags` (the kernel's authoritative answer) is captured

```c
kbase_kmod.c:1693  alloc_flags = req.out.flags;   /* KBASE_IOCTL_MEM_ALLOC_EX */
kbase_kmod.c:1710  alloc_flags = req.out.flags;   /* KBASE_IOCTL_MEM_ALLOC    */
kbase_kmod.c:1753  kbase_bo->base.backend_mem_flags = alloc_flags;   /* v73: new */
kbase_kmod.c:1590  kbase_bo->base.backend_mem_flags = req.out.flags; /* v73: import path */
```

This matters because **the kernel is allowed to add bits**: the pre-existing import log at
`kbase_kmod.c:1589` already shows `import flags=0x4040f -> outflags=0x4540f` — the kernel *added*
`0x5000`. So the flags **we request are not sufficient evidence**; the diagnostic therefore prints
what the kernel **granted**. If the backend recorded nothing the line says so explicitly rather than
printing a fabricated value.

## 4. Why `atomic-capable` is reported as `unknown` (and not guessed)

Grepped facts in this tree:

- `to_kbase_mem_flags()` (`kbase_kmod.c:1450`) sets `BASE_MEM_COHERENT_LOCAL` (`:1456`), then
  **clears it for every CSF_EVENT BO** (`:1483-1484`) and only sets `BASE_MEM_COHERENT_SYSTEM`
  when `PAN_KMOD_BO_FLAG_IO_COHERENT` was requested (`:1476-1477`).
- Our seqno BO requests **only** `PAN_KMOD_BO_FLAG_CSF_EVENT` (`panvk_vX_gpu_queue.c:1001-1002`),
  and the kbase backend **hardcodes** `props->is_io_coherent = false` (`kbase_kmod.c:362`), so
  `pan_kmod_bo_init` (`pan_kmod_backend.h:90`) never auto-adds `IO_COHERENT`.
- ⇒ the **requested** kbase flags for the seqno cell are
  `PROT_CPU_RD|CPU_WR|GPU_RD|GPU_WR (0xf) | BASE_MEM_SAME_VA (0x2000) | BASE_MEM_CSF_EVENT (0x80000)`
  = **`0x8200f`**, with **no `COHERENT_SYSTEM` (0x400) and no `COHERENT_LOCAL` (0x800)**.
- `mali_base_csf_kernel.h:35-45` says that when outer-shareable coherence is not specified or not
  available, **kbase itself falls back to an uncached GPU mapping**; `mali_base_common_kernel.h:121-127`
  adds that the 3 shareability flags are ignored for GPU-uncached memory.
- **Nothing in this tree** maps any of those bits onto whether a *system-scope atomic* is serviced
  (the uapi has no atomic-capability bit).

⇒ the honest verdict is **`unknown`**, with the decidable bits printed alongside so the next round can
decide from data instead of speculation. **This is not a claim that the GLM hypothesis is right.**

## 9. Interpretation table (how to read the v73 log)

The v73 run is identified by its `kbase: ATOMIC …` lines appearing next to `kbase: CKPT …`.

| observation | reading | next step |
|---|---|---|
| `ATOMIC in-range = no` | The atomic target is **outside** the 4096-byte seqno BO — a real bug in our VA/stride bookkeeping (`:247` stride must be 64, `:1030` base comes straight from `pan_kmod_vm_bind`). | Hard bug, not a hypothesis: re-check `kbase_seqno_stride()` / subqueue index vs `PANVK_SUBQUEUE_COUNT`; the `+offset` printed on the target line shows which term is wrong. |
| `in-range = yes`, `kernel COHERENT_SYSTEM bit10 = clear` | The seqno cell is **not outer-shareable / not system-coherent**. This is the one datum that makes the GLM "attribute mismatch" hypothesis concrete rather than speculative — a system-scope atomic landing on non-outer-shareable memory is the classic silent-hang case. | Try the one-line fix candidate below and re-run the same test. |
| `in-range = yes`, `bit10 = set` | The kernel **did** grant outer-shareable coherence ⇒ the **attribute-mismatch hypothesis is refuted**; the SYNC_ADD64 operand attributes are fine, so look elsewhere (deferred-sync slot / `SB_ID(DEFERRED_SYNC)` bookkeeping, or the CS never issuing the op). | Do not chase memory attributes; instrument the deferred-sync scoreboard slot instead. |
| `atomic-capable = unknown` with `backend_mem_flags = 0` and "backend did not record one" | The kernel flags were not captured (non-kbase backend, or the field was not filled) — the mem-flags line carries only our *requested* `bo->flags`. | Re-check that `kbase_kmod.c:1753` ran (the alloc path is taken, not the import path). Confirm from the alloc-time log line. |
| `in-range = yes`, `bit10`/`bit11` both clear, but a **prior** job in the same run completed | Weakens the pure-attribute story: the same cell/attributes worked before ⇒ something about *this* job's operands/slot state differs. | Compare `ATOMIC target addr` across a succeeding and the failing job. |
| `ATOMIC` lines absent entirely | The timeout snapshot did not run, or `subq->kbase.user_io` / `ringbuf_cpu` was NULL (`:837` early-return). | Check the CKPT lines; if they are present but ATOMIC is not, the build is not v73. |

### One-line fix candidate (NOT applied — candidate only)

Only if the log shows `kernel COHERENT_SYSTEM bit10 = clear`, the candidate is to ask kbase for
system-coherent memory for the seqno cell, at **`panvk_vX_gpu_queue.c:1001-1002`**:

```c
      pan_kmod_bo_alloc(dev->kmod.dev, dev->kmod.vm, 4096,
                        PAN_KMOD_BO_FLAG_CSF_EVENT | PAN_KMOD_BO_FLAG_IO_COHERENT);
```

`to_kbase_mem_flags()` then adds `BASE_MEM_COHERENT_SYSTEM` (`kbase_kmod.c:1476-1477`), giving the
seqno cell outer-shareable (system-coherent) attributes. **This is a candidate, not a conclusion:**
`props.is_io_coherent` is hardcoded `false` in this backend (`kbase_kmod.c:362`) and
`mali_base_csf_kernel.h:35-45` says kbase already falls back to an uncached GPU mapping without
outer-shareable coherence — so it is genuinely open whether adding the flag changes anything. It
must not be applied until the v73 log says `bit10 = clear`.
