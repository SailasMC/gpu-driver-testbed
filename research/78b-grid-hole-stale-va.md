## 1. ⇒ 结论（把你的新方向**从假设升级为结构性结论**）

> **GPU 访问的地址是"分配器栅格上的一个槽位"，但那个槽位当前没有存活 BO；而在 v115，紧邻的槽位曾被一块 `panvk_pool_alloc_backing` 的 64 KiB slab 占据。**
> ⇒ **⇒ 某个结构里仍保存着"BO 曾经（或以为）在那里"的地址** ⇒ **"过期/错位 VA"成立** ✓✓

**这条同时解释了你 6 个版本里所有令人困惑的数据**：
| 现象 | 解释 |
|---|---|
| 故障随**设备初始化期**布局变 | BO 被放到别处 ⇒ **空洞与其栅格位置**跟着变 ✓ |
| 不随**每 cmdbuf** 池 slab 变（E1/E2） | 持有者**不在**那个池里（改池尺寸只挪动 slab，没动持有者）✓ |
| v118（geometry 32 KiB）故障"精确移动 0x8000" | **不是** geometry 相关：那次改动**挪动了分配栅格**，于是**另一个过期槽位先触发** ✓（v120 同时出现两个地址，正是"多个候选里谁先触发"）✓ |
| v120 两个地址同时出现 | 有**两个**过期槽位都在同一空洞里，谁先被访问取决于时序 ✓ |
| 只有真 draw 触发 | 只有 draw 会消费这些结构（descriptor / 描述符环 / tiler 包）✓ |
| geometry 填充（v119/v120）无效 | 因为根因不是 geometry 内容 ✓（但该修复保留）✓ |

**⇒ 因此：geometry 线的全部实验（v118–v120）应记为"噪声"**，与你的自我修正一致 ✓

## 2. 你第 2 点：`site=0xbe8e28/0xbe8e34` 是什么（**顺带结清"一次运行两个 utrace BO"悬案**）

- 两个 site 相差 **0xc = 12 字节** ⇒ **同一条调用路径上的两个相邻打印点**（不是两次分配）✓
- 而这一局里**只有一块 10 MiB 的 utrace BO** ⇒ **干净局里只有一个 heap BO** ✓
- **⇒ 悬案结清**：此前"一次运行出现 256 MiB + 1 MiB 两个 utrace BO"是**日志混行**（两者 VA 区间**重叠**，同一 VA 空间不可能）⇒ **你的 env A/B 是可靠的** ✓（建议把 `PID + dev 指针` 加进那行打印，永久消除）✓

## 3. 你第 1 点：**"GPU 为什么去读 utrace BO 末尾之后"** —— 答案要改

- `tri` **不做 capture**（你已定论）⇒ **没有任何代码应该把 heap 地址交给固件** ⇒ **所以这不是"堆内越界/堆尾溢出"**，而是**别的持有者手里有一个"落在空洞里"的地址**；
- 空洞里**曾经有过**一块 `site=0x9c8270` 的 slab（v115 实测）⇒ **最自然的来源 = 那个 slab 的地址被某个长期结构缓存下来，而 slab 已经被回收/搬走** ✓✓
⇒ **⇒ 攻击面从"utrace 堆"整体转移到"谁缓存了池 slab 的地址"**（正是我 78 号 §2 的首要嫌疑）✓

## 4. 你第 3 点：**"过期 VA"的落点（按嫌疑排序）**

| # | 持有者 | 为什么 |
|---|---|---|
| **1 ★** | **命令缓冲池支撑的地址**（descriptor chunk / 命令流 / push constants 的 `addr.dev`）被写进 **descriptor 或长期 ctx** | 池 slab 在 **cmdbuf reset / pool 回收** 后搬走/释放，而缓存方不更新 ⇒ 地址落进空洞 ✓；v115→v120 之间 cs/desc 池 slab 从 64 KiB 变 256 KiB 并**整体挪位** ⇒ 恰好制造这种"旧地址落空" ✓✓ |
| 2 | `cs_ctx->render.{tiler_heap, geom_buf, desc_ringbuf.ptr/syncobj}`、`tiler_oom_ctx.ir_scratch_fbd_ptr` | 写于 queue init（`:2832-2858`）；若相关 BO 被重建/搬移而未刷新即过期 |
| 3 | `subq->context` 里的 `syncobjs`/`regs_save`（`:2815-2822`） | 同上，写一次，长期持有 |
| 4 | 续租/retire 后的 `context.dev_addr` | 对 **tri 无效**（阈值够不到），只对长跑有意义 |

## 5. 你第 4 点：下一个 5 分钟实验（**这次能直接点名凶手**）

### E1（★首选，1 次重编，~15 行）：**分配/释放时间线**
现在的 v115/v120 打印只有**分配**。加 **释放** 与**单调序号**：
```c
/* panvk_pool_alloc_backing 成功处 与 panvk_priv_bo_create 成功处： */
mesa_logi("BO+ #%llu va=[0x%" PRIx64 ",0x%" PRIx64 ") size=0x%" PRIx64
          " flags=0x%x site=0x%zx", ++bo_seq, va, va + size, size, flags, site_off);
/* 对应释放点（pool cleanup / free_mem / priv_bo_destroy / cmdbuf reset）： */
mesa_logi("BO- #%llu va=[0x%" PRIx64 ",0x%" PRIx64 ") size=0x%" PRIx64 " site=0x%zx",
          ++bo_seq, va, va + size, size, site_off);
```
**判据**：故障发生时，把 `[0x5fffe00000, 0x5ffffa0000)` 这个空洞**与时间线对照** ⇒ **哪一块 BO 在该区间被释放/搬走** ⇒ **它的 `site_off` 就是"谁曾经在那里"** ⇒ 持有者随之暴露 ✓✓
**为什么这条最有价值**：它把"空洞"从"未知区域"变成"**有历史的区域**"，而 v115 的交叉验证已经告诉我们那里确实住过一块 `0x9c8270` 的 slab ✓

### E2（与 E1 同版，~40 行，DEBUG-only）：**GPU 地址来源校验器**
在把任何 GPU 地址交给 CS 之前（至少 `cmd_draw.c:1356` 的 `tiler_heap/geom_buf`，以及每个 descriptor / ring 指针写入处）断言该地址落在**当前存活**的 BO/slab 区间内（区间表就来自 E1 的增删记录）⇒ **直接点名那个过期字段**（谁、哪个结构、指向哪）✓✓

**建议**：**E1 + E2 同一版**（E1 给"那里曾是谁"，E2 给"现在谁还在指它"）—— 这两条一起上，基本可以把凶手钉在 1~2 个字段上 ✓
